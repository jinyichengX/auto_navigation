# AI agent 编译/构建通用经验

## 1. "编译不能保证"的根因

AI agent 最容易犯的编译错误不是算法错了，而是**项目结构 + 构建系统层面的惯性跳过**：

```
agent 写代码
  ↓
顺手 include 了一个头文件（比如 rrt.h 里的 "kdtree.h"）
  ↓
头文件在磁盘上确实存在（我复制过来了）
  ↓
agent 默认假设编译器能找到它
  ↓
但 CMakeLists.txt 的 include_directories 没配对
  ↓
编译失败：fatal error: kdtree.h: No such file or directory
```

同理：

```
agent 在 namespace A 里定义 Params struct
  ↓
另一个文件在 namespace B 里直接写 Params params_
  ↓
agent 默认假设编译器能自动跨 namespace 找
  ↓
但 C++ 不会自动跨 namespace 找
  ↓
编译失败：error: 'Params' does not name a type
```

**本质：agent 写代码时脑子里知道文件在哪、类型在哪，但编译器不知道。agent 没有做"编译器视角"的核对。**

## 2. 可执行检查表（任何编译任务前必过）

### 2.1 头文件 include 路径和 CMakeLists include_directories 对齐

对于 `add_executable(X ...)` 的每个源码文件里的 `#include "Y"`：

- [ ] Y 到底在磁盘上的什么位置？（从项目根目录算）
- [ ] CMakeLists.txt 里的 target_include_directories 有没有一条路径让编译器能搜到 Y？
- [ ] 如果是第三方子库（比如 kdtree），它自己内部的 `#include "X"` 期望的 include 根是什么？我设的 include_directories 是不是匹配它期望的根？

**典型坑**：
- kdtree.c 内部写 `#include "kdtree/kdtree.h"`，期望 include 根是 `.../official/`（这样加上 kdtree/ 子目录就能找到）
- 我之前设成了 `.../official/kdtree/`（多了一层），编译器就会去找 `official/kdtree/kdtree/kdtree.h` → 不存在

### 2.2 namespace 边界

- [ ] 每个新写的 .cpp 文件，在什么 namespace 里？
- [ ] 用到的类型（Params、RrtTree、LocalOctomapManager）在什么 namespace 里？
- [ ] 有没有加 `using` 或者写全限定名 `outer::inner::Type`？

**典型坑**：
- `tree.h` 里 `namespace nbvInspection { struct Params { ... } }`
- `nbvplanner_explorer.cpp` 里 `namespace nbvplanner_ros2 { ... Params params_; ... }`
- agent 脑子里知道 Params 在那，但编译器不会跨 namespace 自动找

### 2.3 静态类型检查工具 + 真正的构建

- [ ] 写完所有文件后，agent 至少应该做一次文件级别的 grep：每个 include 的文件在磁盘上都有吗？
- [ ] 每个 .h / .cpp 里的类型引用，在 namespace 范围内能找到吗？

**agent 不做真正的构建（遵守用户规则），但必须做等价的静态核对。** 之前完全没有做这步，导致两个低级错误一起暴露。

### 2.4 CMakeLists.txt 依赖和源码文件同步

- [ ] add_executable 的源文件列表和磁盘上实际存在的文件一致吗？
- [ ] ament_target_dependencies 里的 ROS2 包名，find_package 里有没有 find 过？
- [ ] target_link_libraries 里的外部库（比如 OCTOMAP_LIBRARIES）find_package 里有没有 find 过 OCTOMAP？

### 2.5 删除旧文件后同步更新 CMakeLists

- [ ] 旧文件删了，CMakeLists 里 add_executable 的源文件列表是不是也删了对应的条目？
- [ ] 如果旧文件有 target_sources / target_link_libraries，是不是也同步清理了？

## 3. 记住这一点

> **"文件在磁盘上" ≠ "编译器能找到" ≠ "类型在当前 namespace 里可见"。**
> agent 脑子里的"我知道在哪"和编译器实际能搜索到的是两套系统。
> 每次换 CMakeLists 的 include_directories，每次写跨 namespace 的类型引用，都要停下来核对一次。

## 4. 这次踩坑的具体教训

| 错误 | 根因 | 应该做什么 |
|---|---|---|
| `kdtree.c: fatal error: kdtree/kdtree.h: No such file or directory` | kdtree.c 里写 `#include "kdtree/kdtree.h"` 期望 include 根是 `.../official/`，但我设成了 `.../official/kdtree/` | 复制第三方子库后，先读它的源码内部 #include 模式，再反推正确的 include 根目录 |
| `error: 'Params' does not name a type` | `Params` 在 `nbvInspection` 里，用它的文件在 `nbvplanner_ros2` 里，没加 `using` 或全限定名 | 写跨 namespace 引用时，要么加 `using A::Type;`，要么写全限定名 `A::Type` |
| 两个错误同时暴露 | 写完文件后没有做"编译器视角"的静态核对就交付了 | 写完所有文件后，至少花 30 分钟：grep 所有 include → grep 所有类型引用 → 核对 namespace → 核对 CMakeLists |
