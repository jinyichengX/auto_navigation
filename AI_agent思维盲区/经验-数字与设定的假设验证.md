# 通用经验：从文件读到数字/设定 → 惯性当成正确答案 → 是 AI agent 最常见的连续失败模式

## 这个模式长什么样

```
agent 从 grep / 配置文件 / 源码 / 文档里看到一个数字或设定
    ↓
惯性地认定"这个数字是对的"
    ↓
跳过"这个数字到底是怎么被解析的、运行时实际会产生什么行为"这一步
    ↓
直接改代码 / 给命令 / 让用户跑
    ↓
用户验证失败
    ↓
agent 第一反应：外部系统有问题（Gazebo spawn、ROS2 QoS、PX4 参数...）
而不是：自己选的数字本身到底对不对
```

## 这个模式出现在哪些任务里

不限于坐标、spawn。任何任务只要涉及"从静态文件里拿东西然后用"，就容易中招：

| 任务类型 | agent 容易跳过的验证 |
|---|---|
| 选出生点坐标 | spawn pose 在 world frame 下真的有模型覆盖吗？这个 tile 在 spawn pose 的 z 层吗？ |
| 改 OctoMap Z 过滤范围 | min_z/max_z 到底会丢掉哪些点？这些点对下游任务重要吗？ |
| 改 NBVPlanner 参数 | gainRange、degressiveCoeff 在实际 OctoMap 里会产生什么效果？不是论文里的，是你的地图里的 |
| 改阈值/边界 | 这个阈值在当前数据分布下的实际效果是什么？不是"调小了更保守"这种定性描述 |
| 消息格式/字段 | 消息里这个字段真的有值吗？不是"文档说这个字段存在" |
| TF 变换链 | 这个 TF 真的在发布吗？不是"代码里有 broadcaster" |
| 参数解析顺序 | 环境变量、YAML、命令行参数的优先级和解析顺序是什么？不是"应该是按这个顺序" |

## 真正通用的做事流程

### 1. 不要"看到什么就用什么"，先停下来问三个问题

不管这个数字从哪来（文件、grep、文档、用户说的），先在脑子里过一遍：

| # | 问题 | 跳过的后果 |
|---|---|---|
| 1 | **这个数字在运行时到底会被谁解析？解析逻辑是什么？** | 环境变量的 x,y,z 顺序可能不是你想的顺序；YAML 的 frame_id 可能被 launch 覆盖 |
| 2 | **这个数字对应的运行时实际行为是什么？不是文件里写的语义。** | 文件里写 `<pose>0,0,0</pose>` 不代表模型真的覆盖 (0,0,0)；文件里写 `point_cloud_max_z: 2.5` 不代表 2.5 以上真的"不应该"保留 |
| 3 | **从已知有效的参考点/参考配置出发，我这次改了多少？是不是小步？** | 从一个有效坐标跳到几百米外，跳过中间所有验证 |

### 2. 全景整理比单步选点重要

任何"选点/选值"类任务，先把**所有可能选项完整列出来**，再从中选，而不是看到一个就用：

```
❌ 坏做法：grep 到一个 x=59.12 的数字 → 直接用
✅ 好做法：grep 所有选项 → 按关键维度（如 z 值）分层 → 排除无效层 → 再从有效层里选
```

### 3. 失败后的归因顺序（从最可能到最不可能）

```
1. 我选的数字/设定本身对不对？
2. 这个数字有没有被正确解析？
3. 坐标系/单位/顺序对不对？
4. 进程有没有残留？
5. 上下游系统有没有正常运行？
6. 最后才是：是不是代码逻辑有 bug？
```

**绝大多数情况下，agent 会直接跳到第 6 项（归因外部），而跳过前 1~3 项。** 因为前 1~3 项需要回头验证自己的假设，心理成本高。

### 4. 任何修改后，让用户做最简单的视觉/运行时验证

不要让用户直接跑完整链路，让他先看最基础的东西：

- "重启后打开 Gazebo GUI，飞机 Follow 后在巷道里吗？"（而不是"跑完整链路"）
- "ros2 topic echo 一下这个字段真的有值吗？"（而不是"改完应该就对了"）
- "在 RViz 里确认这个 TF 真的在发布吗？"（而不是"broadcaster 代码在那里所以应该有"）

**一个运行时的视觉确认，比任何静态分析的信心都靠谱。**

### 5. 跨项目通用的数字来源可靠性排序

```
最可靠：用户已经在 GUI 里验证过的运行时数值
    ↓
次可靠：agent 自己查源码 grep 到的解析逻辑
    ↓
    ↓
不太可靠：静态文件里的数字（SDF pose / YAML 参数 / launch 里写的值）
    ↓
最不可靠：文档里写的、agent "应该如此" 推测出来的
```

**文件里的数字永远是假设，运行时才是事实。** 不管是 SDF、YAML、代码里的硬编码，写完之后它可能被覆盖、可能被偏移、可能在不同坐标系下、可能只在特定层有效。

## 记住这句话

> **任何数字/设定从文件里读到的时候，都是"待验证的假设"，不是"正确答案"。** 惯性跳过验证就直接用，是 AI agent 在配置类任务上连续失败的最常见根因。
